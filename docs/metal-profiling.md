# Metal profiling and native-code gate

Probe does not promote a kernel from tokens per second alone. Every retained candidate must pass
the same loop:

1. compile the exact embedded Metal source used by the runtime;
2. materialize the device-specialized `applegpu_g16s` pipeline;
3. inspect and hash its native slice;
4. measure the isolated kernel with GPU timestamps and a CPU reference;
5. profile the full inference graph with the candidate disabled and enabled;
6. run alternating, repeated throughput trials; and
7. confirm deterministic model output.

The isolated result diagnoses the kernel. The full-model result determines whether it matters.
Neither result substitutes for the other.

## Public capability boundary on the M4 Pro

Run:

```bash
make metal-tools
build/tools/metal-counter-info
```

On the reference M4 Pro, Metal reports:

- stage-boundary counter sampling: supported;
- dispatch-boundary counter sampling: unsupported; and
- exposed counter sets: `timestamp` containing only `GPUTimestamp`.

This is a runtime `MTLDevice` capability query. Calling
`sampleCountersInBuffer:atSampleIndex:withBarrier:` around individual dispatches when the device
returns false is invalid; Probe must not present it as working instrumentation.

Probe can still isolate one kernel in a compute pass and attach timestamp samples to the start and
end of that encoder. `metal-moe-reduce-bench` uses this route. It reports a per-sequence duration
from stage-boundary GPU timestamps, retains every sample, alternates reference/candidate ordering,
and checks both paths against a CPU result. Splitting a production graph into extra encoders would
perturb scheduling, so this mechanism is diagnostic-only.

For full-graph attribution, use an unmodified Metal System Trace and an Xcode GPU capture:

- Metal System Trace preserves command-buffer duration, overlap, CPU-to-GPU latency, driver work,
  and host scheduling.
- Xcode capture/replay can collect command-level GPU counters, shader-profiler samples, occupancy,
  limiter, and bandwidth information. Replay serializes work for some measurements, so it is a
  bottleneck diagnosis rather than a throughput benchmark.

## Native G16 artifact

Compile the exact generated source rather than a handwritten excerpt:

```bash
xcrun -sdk macosx metal -O3 -I .cache/llama.cpp/ggml/src \
  -c .cache/llama.cpp/build/ggml/src/ggml-metal/autogenerated/ggml-metal-embed.metal \
  -o build/profile/ggml-metal.air
xcrun -sdk macosx metallib build/profile/ggml-metal.air \
  -o build/profile/ggml-metal.metallib
```

`metal-pipeline-archive` asks the M4 Pro driver to specialize a named function and serializes its
`MTLBinaryArchive`. Pass `NSG=0` for a function without the Q4 matrix-vector constants:

```bash
build/tools/metal-pipeline-archive \
  build/profile/ggml-metal.metallib \
  build/profile/kernel.binaryarchive \
  kernel_moe_weighted_sum_f32 0 0 0 0
xcrun metal-lipo build/profile/kernel.binaryarchive -thin applegpu_g16s \
  -output build/profile/kernel.g16.metallib
xcrun metal-objdump -h build/profile/kernel.g16.metallib
shasum -a 256 build/profile/kernel.binaryarchive build/profile/kernel.g16.metallib
```

This proves which device program the driver emitted and exposes native code size, section layout,
and binary changes between candidates. It is stronger than inspecting AIR alone.

## Direct native execution and remaining ISA gap

The installed Apple native translator accepts `applegpu_g16s`, and `metal-objdump` recognizes the
extracted slice as 64-bit Apple-GPU Mach-O. The installed disassembler nevertheless returns
`no instruction printer for target agx3---macho`.

Probe has gone below that tooling boundary. Differential compilation isolated an immediate field
in a native G16S instruction, and a one-byte patch changed a `+1` GPU kernel into a synthesized
`+3` kernel through a required `MTLBinaryArchive` hit. See [direct-isa.md](direct-isa.md) for the
reproducer and adversarial controls.

This establishes a practical native-patching route, not a general assembler. Register allocation,
instruction scheduling, control-flow encodings, descriptors, and most instruction semantics remain
undocumented. MSL plus device specialization remains the production kernel path; differential
native patching is an experimental final-mile option with a CPU oracle and exact archive controls.
